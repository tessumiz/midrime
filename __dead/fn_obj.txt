Basic syntax
————————————

foo:
  // void func; 0 args

foo(i32 a, b, c, u8 d):
  // a, b and c are all i32

foo -> i32:
  give 13  // return kwd

foo:
  give 15  // implicit return; used only when the compiler can decipher it easily


Overloading is supported in a new syntax:

foo:
  (i32 a, f32 b) -> str: ...
  ():  ...
  (list<u32> l): ...


Multi-return funcs:

foo -> (i8, str):
  give 5, "abc"  // this is NOT an array; it's stored as a list of expr in the frontend


i8 a, str b = foo()
// a, b = foo()  works too

For ignoring a val, use _:

_, s = foo()


Default args:

foo(list<i32> a=?, b, c=?): ...
foo(b: [1, 2, 3])


Stack frame
————————————

The first frame will be the global frame; it has no prelude.

[bulk: arrs/objs/spills] [prelude: ret_ip: 4B | ret_fp: 4B] [slot-0 | slots1-n]
                                                              ^ fp points to slot-0

bulk must be 4B-aligned.

slot-0 is reserved for self/closurefp. If none of this apply, stores garbage data. This slot is
treated special. The reason why this doesn't get reserved for the slot right after the arg
is that that would require storing arity as metadata and logic for reading it, which is made easy
by permanently trading the first slot.


Func-storage
------------

FUNC:
[bulk_plus_prelude_sz: 2B | slots_used: 2B]  // metadata header; each field is 4B-aligned
[instrs]
...
[RET]


The CALL/DYN_CALL instrs store ptrs to this header; FP is set to SP + bulk_plus_prelude_sz (4B-
strided), prelude is set and SP set to FP + slots_used (again, 4B-strided).

Funcs are almost never going to have a bulk-size of 256KB (that's a quarter of the 1MB stack).

For CALL, the compiler makes the caller populate the args (including the default args). DYN_CALL
doesn't have default args (as that would require storing arity and defaults, a low-ROI abstraction).


Targeted-copy
—————————————

Certain optimizations are tried by the compiler if there is an overlap between the caller and the
callee frames. Assuming a comfortable overlap region:

(i) If the callee is not a void fn,

  (a) If retval is either numeric, seq, hashtype or a ref, slots 1-n ('n' if multi-ret) would
be used for return vals. This could be directly read by the caller without needing an [LDI]. This
is only benefitial if the return is part of an expr, saving a load instr to a temp var.

  (b) If retval is an obj, slots 1-n MUST store the dest-refs where the objs would be written to.

* Arrays can only be returned if they persist in the stk (either in GLO,
or an upval), or if it's a heap arr. These DON'T follow the retval semantics of objs.

(ii) The subsequent args (after retval) are used for args. If args are exprs, the target can be
directly written into the callee's slots (if they overlaps with the caller's).

(iii) Regular [LDI/STOI] would be used for all other cases (either if overlap is minimal most prolly
due to heavy SROA, or if args/ret aren't part of exprs).


A PRIOR NOTE:

A dual-stack arch (regstk + datastk) wasn't decidebecause of a less ROI (higher complexity, extra
CPU reg pinning, more state management instrs). The only real benefit was a near-guaranteed frame
overlap possibility even if the callee has a heavy bulk (since it would go in the datastk).

Even so, zero-copy would anyways be a micro-optimization since heavy bulk implies more exec time.


SROA
————

The 'xy' obj utility family is dynamically generated by the compiler as per use; only the variants
which are used in the codebase will be generated:

cls xy: i32 x, y
cls xyu: u32 x, y
cls xyf: f32 x, y
cls xyu8: u8 x, y
...

SROA will only be used for small objs, never arrays, hence why it's advisable to store pairs as xy
objs than in an array (which would anyways have an 8B len+cap overhead).



Func as dtype and upvals
————————————————————————

Funcs are first-class citizens. They are always stored as a fat ptr, a pair of fnptr and closurefp:

foo(i32 a) -> str: ...

// [fnptr: 4B | closure_fp: 4B] is stored, where cptr == ? in this case
(i32, f32 -> str) a = foo  // or just: a = foo
a(25)

(i32, f32 -> str) a  // stores fnptr == ?; a is ? is true


If 'foo' is overloaded, the first overload is chosen. If you need to choose it manually:

a = foo(i32, i32 -> str)  // another overload, say

By default, all global fields can be accessed inside any scope (through LDI).


Closures
========

foo:
  x = 5
  bar:
    give x

  qwe:
    give 2 * x

  f(bar)
  f(qwe)
  bar()


Rules
------

0. Funcs cannot be returned, and upvals can only be propagated down once (no chained closures).

1. Even if the func doesn't have any upvals, it must use the same 8B ABI; [fptr | ?]

2. The type is ref by default; SROA isn't allowed on func fat ptrs. 'foo' stores a fat ptr each
for each closure func. It starts with:

[LDA_FPO]  [$t] [0]  // loads current FP
[RSHFT_U_I] [$t] [2] // divide by 4
[STO_FPO]  [$t] [off__bar_fat_closure_fp]  // offset is known at compile-time
[LDVAL_19] [$t] [&foo.bar]  // loads bytecode-addr (4B-strided)
[STO_FPO]  [$t] [off__bar_fat_fnptr]
...  // the same for off__qwe_fat


3. Before each call/passing of a closure func, this is hardcoded by the compiler:

[LDA_FPO] [$t] [off__fat]
// or directly loaded into callee's arg if being passed; else DYN_CALL called directly on $t:
[DYN_CALL] [$t]  // note; doesn't allow default vals

Cls & obj
—————————

You can have classes inside classes, but not classes inside funcs. Classes can have enum
defns inside, as well as "alias" kwd.

Static fields are not stored together as a struct; they are stored scattered and separate in
the globals section (as static fields are mutable).

While methods can't be called/passed around as B.method(self), static funcs can (since their
first arg is not special data going to vreg-0).

cls A:
  static:  // stored in the globals section
    i32 i  // init with 0
    f32 f

    bar: ...  // static-methods are allowed to be called like A.bar()

  // could also be static i32 a, b; static f32 c

  str s  // instance field
  char c
  c
  init:  // overloading allowed
    (i32 a, b, c=4):
      @fill  // the same as $a = a; $b = b; $c = c
    (): ...  // empty overload

  foo:
    a = i
    i = 3  // creates a local
    $i = 3 // assigns to the field


  kill:
    // destructor; called for stk objs when they go out of scope
    // for hp, use 'kill obj' for calling destr
    // DOES NOT invoke GC


Note: Even if the $ sigil denotes self, $.a isn't valid; use $a. Method calls from within
must use $.foo(), and it can also be passed as an arg; func(5, $, 10)


Copy-semantics
==============

A a(1, b=3)  // illegal; use a = A(1, b = 3) instead
A a = {1, b=3}  // struct constr
A a {1, 2}  // illegal

A a  // init not called; default/garbage data

A a = { 1, b = 3 }  // if '=' not present, rval treated as set expr; the semantic analyser
must check if there isn't a op=(set s) defined and treat it as struct assignment

a = A { 1, 2 }  // rval is a stack obj now
a = A(1, 2)
a = box A(1, 2) or box A{1, 2}  // heap init
[ALLOC] [$hp] [8]  // just '4B str + 1B i8 + 3B padding
[REGCPY/STO_FPO] [$hp] [<arg slot of A_init>]
[CALL] [A_init_ptr]


Struct-unpacking:
{ field1, field2, field3 } = obj


Inheritance
———————————

Both true inheritance and mixins are allowed. Use 'v' to mark a method as virtual
(yes, follows Cpp-like inh, not like Java). Use the '<-' op for inheritance:


cls Base:
  static:
    k = 0
    qwe: ...
  
  a = 1, b = 2

  init:
    (): ...
    (i32 a, b=5): @fill

  v foo: ...
  bar: ...


cls Child <- Base:
  // static vars are shared with base

  b = 5  // inh field re-assigned; there is no "field-overriding" (aka masking)
  c = 6  // new field

  foo(i32) -> str:
    give 10  // auto-cast to str(10) aka "10"


Every class with at least one virt method will have a vtable ptr as the first field. This
i32 _vptr_<id> can't be accessed directly.

For each class inheriting from a base-class with at least one virtual method, a vtable
will be created in the cnst section and its ref will be stored in the first field. Vtable
is just an arr of 4B fnptrs.

Dyn dispatch would use:
[V_CALL] [$obj] [voff: 19]  // since $_vptr is the header, passing $obj is identical


Multi-level inheritance is fully supported by default. Once a method is virtual, it must
always remain so, which means no 'v' tag is necessary here:

cls A:
  v foo: ...
  bar: ...

cls B <- A:
  foo: ...  // overridden
  bar: ...  // illegal; A.bar must be marked v

cls C <- B:
  foo: ...  // B.foo is v by default; overridden


No optimzation will be there to share vtables if overrides are absent.


Mixins
——————

Mixins are to be treated purely as template-makers:

cls A:
  + B:
    incl foo, bar, x

  + C:
    excl init

  + D, E  // includes all, including init

  + F, G: ...  // can't incl/excl with comma-sep syntax

  ...


Its sole purpose is to prevent repetition of code by copying from templates. Hence, they don't
break the classic is-a inheritance. For accessing masked data (say 'x' was masked), use B.x.

Virt methods will be mixed as plain methods. Also, static fields are not shared, but copied over
so that there will be a new set of static fields. Any definitions inside (cls/enum/etc.) will
not be copied over.

Mixins NEVER mask instance data; the opposite happens.


Operator overloading
————————————————————

Overloads are NOT commutative.

cls Foo:
  op+(Bar bar) -> Qwe:
    // Pine + Apple -> Pineapple kind of heterogenuity

  ...  // +-/*&|  op and()  op or()

  // for all other ops too. Operator precedence is the same as usual, so beware of op< and op>
  // overloads for seq/dict [i] get/set don't exist yet

  hash -> u32:
    // this MUST be the signature

  cast u16:
    // return u16


Thunks for comparing generics WON'T be created; make the custom func yourself.


Implicit arg cast
-----------------

f(T t, U u)

This is particularly a pain when the func is overloaded. Hence, a scoring system is used to
decide this in the semantic analysis phase. First, the type tuple is checked. If no direct
overloads are found, an arity check is used to yield all overloads with the same no of args.
Out of this, all funcs whose args can be cast to from T, U are filtered. Now, a scoring matrix
is used to filter out the rest, and the first candidate gets called.
